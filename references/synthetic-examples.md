# 合成教学案例

以下内容专为说明工作流构造，不是用户访谈、实际截图、比赛结果或获奖案例。示例没有对应的私人聊天、内部项目、个人账号或原始附件；实际写作应以本次证据替换。

## 案例一：把一个概念讲清楚

**构造需求：** 面向初学者解释缓存命中与未命中，作品允许用户切换请求，看到数据从哪里读取。

先确认读者已知知识、可用工具及比赛允许的交付格式。核心演示是输入同一请求两次，观察第一次读取源数据、第二次使用缓存；改变输入后再次观察。真实运行中采集输入、状态变化和结果画面，图下注明当前请求与可见变化。

正文可按“为什么重复读取慢—输入请求—观察命中状态—解释变化”组织。若没有实际计时，只描述读取路径变化；用户能复述原理可以作为一次理解反馈，不能写成学习效率提升的量化证据。运行失败的画面也不能用设计稿替换后称为已运行。

## 案例二：从反馈到可见的改进

**构造需求：** 为校园活动做一个可筛选的日程页面，用户希望快速找出当天、免费且无需预约的活动。

先把需求转成能验证的动作：选择日期与条件，列表只显示匹配活动。使用合成活动数据，明确这是演示数据。首版反馈若是“筛选入口不明显”，则调整控件位置与标签，再用相同数据、视口和条件采集两张原样截图。

图注描述实际变化，例如“日期筛选移到列表上方，当前条件与结果同时可见”。静态图能证明位置变化，筛选是否正确需要真实操作；没有测量时，不写查找时间缩短百分比。

## 材料整理练习

| 遇到的情况 | 下一步 |
| --- | --- |
| 只有最终截图，没有过程证据 | 检查现存记录；可重跑时标明补录，否则只描述已有证据支持的结果。 |
| 规则限定两页，但案例有很多步骤 | 保留核心操作、输入与结果，调整版面；不私自把关键步骤移到未交付附件。 |
| 截图有真实姓名或通知 | 使用可公开数据与独立窗口重新采集；无法重拍时与用户确定脱敏副本或省略。 |
| 最终包删掉了正文提及的文件 | 同步修正文内入口或按交付约定补齐，再解压验证引用。 |
| 仅要求润色已有材料 | 核对图文证据与声明，不擅自重跑作品。 |

这些案例演示的是决策方式，不规定作品题材、技术栈、页数、截图数量或提交附件。
